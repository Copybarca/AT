# Техническое задание сервиса `document-builder`

## 1. Назначение

`document-builder` собирает один итоговый PDF из полностью подготовленного
набора текстовых элементов и оригинальных изображений.

Сервис получает все материалы одним HTTP-запросом от `trans-api`, проверяет их,
упорядочивает строго по `sequentialNumber`, выполняет книжную вёрстку, создаёт и
валидирует PDF, после чего одним HTTP-запросом отправляет готовый файл обратно в
`trans-api`.

У сервиса один режим работы: **сборка документа**. Вариативных режимов исходного
и переведённого текста, clean/review-профилей и fallback на другой текст нет.
Builder вставляет ровно тот текст, который передан во входном запросе.

## 2. Единственная ответственность

Сервис обязан:

1. принять полный набор материалов одной команды;
2. проверить целостность и последовательность элементов;
3. собрать книгу с заданными правилами вёрстки;
4. проверить созданный PDF;
5. отправить готовый PDF обратно в `trans-api`.

Сервис не должен:

- подключаться к PostgreSQL или любой другой БД;
- читать какие-либо таблицы или SQL-схемы;
- подключаться к S3 или другому объектному хранилищу;
- дополнительно запрашивать текст или изображения после приёма команды;
- извлекать содержимое исходного PDF;
- выполнять OCR;
- переводить текст;
- выбирать между оригинальным и переведённым текстом;
- изменять порядок элементов;
- хранить постоянное состояние книги.

## 3. Сквозной процесс

```text
trans-api
  |
  | один POST: метаданные + elements[] + оригинальные изображения
  v
document-builder
  |
  | проверка входного пакета
  | сортировка и проверка sequentialNumber
  | построение HTML/CSS
  | генерация PDF через WeasyPrint
  | независимая проверка PDF
  v
trans-api
  ^
  | один POST application/pdf: байты готового документа
```

После успешного приёма команды builder не делает GET-запросов за материалами.
Все необходимые данные уже должны присутствовать во входном POST.

## 4. Входной API

### 4.1. Endpoint

```http
POST /internal/v1/builds
Content-Type: multipart/form-data
Authorization: Bearer <service-token>
Idempotency-Key: build-<processId>
```

Один multipart-запрос содержит:

- часть `request` с `Content-Type: application/json`;
- по одной бинарной части для каждого изображения, указанного в `elements`;
- никаких ZIP-архивов;
- никаких ссылок на БД или S3.

### 4.2. JSON команды

```json
{
  "processId": 9001,
  "bookId": 42,
  "resultCallbackUrl": "/internal/v1/books/42/build-result",
  "document": {
    "title": "Название книги",
    "language": "ru"
  },
  "elements": [
    {
      "sequentialNumber": 1,
      "type": "TEXT",
      "text": "Название главы",
      "style": "HEADING_1"
    },
    {
      "sequentialNumber": 2,
      "type": "TEXT",
      "text": "Первый абзац главы.",
      "style": "BODY"
    },
    {
      "sequentialNumber": 3,
      "type": "IMAGE",
      "assetKey": "figure-001",
      "mediaType": "image/png",
      "altText": "Архитектурная схема"
    },
    {
      "sequentialNumber": 4,
      "type": "TEXT",
      "text": "Рисунок 1. Архитектурная схема",
      "style": "FIGURE_CAPTION"
    },
    {
      "sequentialNumber": 5,
      "type": "TEXT",
      "text": "Следующий абзац.",
      "style": "BODY"
    }
  ]
}
```

### 4.3. Бинарные части изображений

Каждый элемент `IMAGE` ссылается на multipart-часть по `assetKey`.

Пример:

```text
Content-Disposition: form-data; name="asset"; filename="figure-001.png"
Content-Type: image/png
X-Asset-Key: figure-001
```

Для одного `assetKey` разрешена ровно одна бинарная часть. Изображения передаются
в исходном виде. Builder не загружает их из другого сервиса и не заменяет
надписи внутри изображения.

### 4.4. Типы элементов

Для первой реализации разрешены только два типа:

- `TEXT` — готовый текстовый фрагмент;
- `IMAGE` — оригинальное изображение.

`TEXT.style` определяет оформление, но не меняет содержимое:

- `TITLE`;
- `SUBTITLE`;
- `AUTHOR`;
- `CHAPTER`;
- `HEADING_1`;
- `HEADING_2`;
- `HEADING_3`;
- `BODY`;
- `LIST_ITEM`;
- `FIGURE_CAPTION`;
- `NOTE`;
- `CODE`.

Неизвестный `type` или `style` является ошибкой входного контракта.

## 5. Ответ на команду

После полной проверки и помещения задачи во внутреннюю очередь:

```http
202 Accepted
Content-Type: application/json

{
  "processId": 9001,
  "accepted": true
}
```

Ответ `202` означает только принятие цельной команды. Он не означает, что PDF
уже собран.

Ошибки входной команды возвращаются до постановки в очередь:

- `400 Bad Request` — повреждённый multipart или JSON;
- `401 Unauthorized` / `403 Forbidden` — ошибка межсервисной авторизации;
- `409 Conflict` — тот же `processId` уже выполняется с другим содержимым;
- `413 Payload Too Large` — превышен лимит команды;
- `422 Unprocessable Entity` — нарушены элементы или последовательность;
- `429 Too Many Requests` — внутренняя очередь заполнена.

## 6. Валидация входного пакета

Builder обязан проверить весь вход до постановки задачи в очередь.

### 6.1. Процесс и callback

- `processId` положительный и присутствует;
- `bookId` положительный и присутствует;
- callback относится к доверенному `trans-api`;
- `Idempotency-Key` соответствует `processId`;
- повтор идентичной команды не создаёт второй worker.

### 6.2. Последовательность

- список `elements` не пустой;
- каждый `sequentialNumber` положительный;
- номера уникальны;
- после сортировки номера образуют непрерывную последовательность `1..N`;
- отсутствуют пропуски и дубликаты;
- исходная последовательность не изменяется после начала сборки.

Builder не пытается самостоятельно исправлять порядок. Команда с пропуском,
например `1, 2, 4`, отклоняется.

### 6.3. Текст

- значение `text` присутствует и не пустое после trim;
- текст является корректным UTF-8;
- отсутствуют незавершённые служебные маркеры;
- размер одного элемента не превышает лимит;
- управляющие символы, кроме разрешённых переводов строк и табуляции в `CODE`,
  отклоняются или нормализуются по явному правилу.

### 6.4. Изображения

- для каждого `IMAGE` существует бинарная multipart-часть;
- каждая multipart-часть используется ровно одним `IMAGE`;
- лишние изображения запрещены;
- разрешены только настроенные MIME-типы, минимум PNG и JPEG;
- фактический формат файла совпадает с объявленным MIME-type;
- ширина, высота и число пикселей находятся в допустимых пределах;
- декодирование изображения выполняется до помещения задачи в очередь;
- имена файлов не используются как пути и не могут вызвать path traversal.

### 6.5. Снимок входа

После валидации builder формирует неизменяемый `BuildInput`:

- нормализованный JSON команды;
- отсортированный список элементов;
- локальные временные копии изображений;
- SHA-256 всего manifest;
- SHA-256 каждого изображения.

Выполняющийся job работает только с этим снимком. Изменение входа после `202`
невозможно.

## 7. Локальная очередь

Внешний брокер не используется. Сервис содержит bounded `asyncio.Queue` и
настраиваемое количество workers.

Правила:

- одна команда сборки является одной неделимой задачей;
- один `processId` одновременно обрабатывается только одним worker;
- очередь ограничена по числу задач и общему объёму временных файлов;
- при заполненной очереди новая команда получает `429`;
- builder не хранит очередь в БД;
- после рестарта незавершённая локальная задача теряется;
- `trans-api` повторяет весь исходный POST с тем же `processId`;
- повторная команда должна быть идемпотентной.

## 8. Алгоритм сборки

### 8.1. Подготовка

1. Получить неизменяемый `BuildInput`.
2. Сверить manifest checksum.
3. Отсортировать элементы по `sequentialNumber`.
4. Ещё раз проверить непрерывность `1..N`.
5. Построить внутреннее дерево блоков без изменения текста.

### 8.2. Группировка блоков

Перед генерацией HTML builder создаёт неделимые группы:

- заголовок + первый следующий содержательный блок;
- изображение + непосредственно следующая подпись `FIGURE_CAPTION`;
- элементы одного списка;
- программный блок `CODE`;
- примечание `NOTE`, если оно помещается на одну страницу.

Если после `IMAGE` нет подписи, изображение остаётся самостоятельным неделимым
блоком. `FIGURE_CAPTION`, не следующий непосредственно за `IMAGE`, считается
ошибкой входного порядка.

### 8.3. HTML

Jinja2 формирует один HTML-документ. Значения текста всегда HTML-экранируются.

Сопоставление:

```text
TITLE          -> h1.cover-title
SUBTITLE       -> p.cover-subtitle
AUTHOR         -> p.cover-author
CHAPTER        -> h1.chapter
HEADING_1      -> h1
HEADING_2      -> h2
HEADING_3      -> h3
BODY           -> p.body
LIST_ITEM      -> li
FIGURE_CAPTION -> figcaption
NOTE           -> aside.note
CODE           -> pre.code
IMAGE          -> img внутри figure
```

Изображения подключаются только из временного каталога текущей задачи.
WeasyPrint запрещается загружать HTTP/HTTPS-ресурсы из HTML.

### 8.4. PDF

Единственный renderer — WeasyPrint:

```python
from weasyprint import HTML

HTML(string=rendered_html, base_url=job_asset_directory).write_pdf(output_path)
```

Builder не использует headless Chrome в production и не содержит альтернативный
ReportLab renderer.

## 9. Обязательные правила вёрстки

### 9.1. Общие правила

- единый формат страниц;
- одинаковые поля на всех обычных страницах;
- единый основной шрифт;
- отдельный моноширинный шрифт только для `CODE`;
- текст не уменьшается индивидуально ради сохранения прежней страницы;
- используется потоковая книжная вёрстка;
- порядок элементов совпадает с `sequentialNumber`;
- builder не добавляет отсутствующий текст и не переписывает содержимое.

### 9.2. Заголовки

- заголовок не разрывается между страницами;
- заголовок не может быть последним элементом страницы;
- заголовок должен остаться минимум с первым содержательным блоком раздела;
- если места недостаточно, заголовок и следующий блок переносятся на следующую
  страницу;
- заголовок главы может принудительно начинаться с новой страницы.

### 9.3. Изображения и подписи

- изображение не разрывается и не обрезается;
- изображение и непосредственно следующая подпись являются единым блоком;
- подпись не остаётся отдельно от изображения;
- если весь блок не помещается в остаток страницы, он целиком переносится на
  следующую страницу;
- если блок не помещается даже на пустой странице, изображение пропорционально
  уменьшается до печатной области с учётом высоты подписи;
- соотношение сторон сохраняется;
- увеличение маленького изображения сверх его естественного размера по
  умолчанию запрещено;
- изображение центрируется и не выходит за поля.

### 9.4. Абзацы

- запрещена одиночная первая строка абзаца внизу страницы;
- запрещена одиночная последняя строка абзаца вверху страницы;
- `orphans` и `widows` по умолчанию равны трём;
- обычный абзац может продолжаться на следующей странице;
- искусственные пустые абзацы не создаются.

### 9.5. Списки

- маркер списка не отделяется от текста пункта;
- по возможности пункт списка не разрывается;
- короткий список не оставляет один пункт на следующей странице;
- последовательные `LIST_ITEM` объединяются в один список.

### 9.6. Код и примечания

- `CODE` сохраняет пробелы и переводы строк;
- длинные строки кода переносятся по настроенному правилу и не выходят за поля;
- короткий кодовый блок не разрывается;
- слишком длинный блок может разрываться только между строками;
- примечание имеет отличимое оформление и не перекрывает основной текст.

## 10. CSS-основа

Минимальные обязательные правила:

```css
@page {
  size: 7in 9.1875in;
  margin: 0.68in 0.72in 0.72in;
}

p {
  orphans: 3;
  widows: 3;

  break-inside: avoid-page;
  break-after: avoid-page;
}

.heading-with-content,

  break-inside: avoid-page;
```

fixture-документах.

```text

BUILD_QUEUE_CAPACITY=4
BUILD_WORKER_COUNT=1
BUILD_MAX_REQUEST_BYTES=1073741824
BUILD_MAX_ELEMENTS=100000

BUILD_MAX_IMAGE_PIXELS=100000000

BUILD_TIMEOUT_SECONDS=1800
BUILD_CALLBACK_RETRIES=3
BUILD_CALLBACK_RETRY_DELAY_SECONDS=5
PAGE_WIDTH_IN=7
PAGE_HEIGHT_IN=9.1875
PAGE_MARGIN_TOP_IN=0.68

```

Секреты не журналируются. При старте сервис проверяет наличие шрифтов и
возможность WeasyPrint создать минимальный PDF.

## 12. Проверка готового PDF

Успешный вызов WeasyPrint ещё не означает успешную сборку.

`pdf_validator.py` обязан независимо открыть файл через PyPDF и проверить:

- файл существует и имеет ненулевой размер;
- PDF читается;
- PDF не зашифрован неожиданным паролем;
- число страниц больше нуля;
- все страницы имеют ожидаемый формат;
- нет страниц без текста и изображений, если пустая страница не была задана
  явным элементом;
- присутствует первый и последний текстовые элементы;
- число встроенных изображений не меньше ожидаемого;
- отсутствуют служебные маркеры незавершённого текста;
- отсутствуют внешние URI на временные assets;
- вычислены SHA-256 и размер файла.

Проверка вёрстки на fixtures дополнительно должна подтверждать:

- заголовок не остаётся внизу страницы;
- заголовок переносится вместе со следующим блоком;
- рисунок и подпись находятся на одной странице;
- рисунок не обрезан и не выходит за поля;
- порядок контрольных текстов соответствует `sequentialNumber`;
- нет необоснованных пустых страниц.

Если validation не пройден, готовый PDF не отправляется.

## 13. Отправка результата

### 13.1. Единственный исходящий бизнес-вызов

После успешной сборки и validation builder выполняет один POST:

```http
POST <trusted-trans-api-base-url><resultCallbackUrl>
Content-Type: application/pdf
Authorization: Bearer <service-token>
X-Process-Id: 9001
X-Book-Id: 42
X-PDF-SHA256: <sha256>
X-PDF-Page-Count: 566
Content-Length: <file-size>

<байты готового PDF>
```

Тело содержит непосредственно PDF. ZIP, multipart и отдельный JSON результата
не используются.

### 13.2. Повторы callback

- повторяется только отправка уже проверенного PDF;
- PDF между попытками не пересобирается;
- число попыток и задержка задаются ENV;
- `processId` и checksum одинаковы во всех попытках;
- успешным считается только HTTP `2xx`;
- после успешного callback временные файлы удаляются;
- если попытки исчерпаны, файл сохраняется до завершения локального job и ошибка
  журналируется; новый бизнес-статус builder не создаёт.

## 14. Ошибки и журналирование

Структурированные логи содержат:

- `processId`;
- `bookId`;
- стадию `RECEIVE`, `VALIDATE`, `LAYOUT`, `RENDER`, `PDF_VALIDATE`, `CALLBACK`;
- длительность стадии;
- число элементов;
- число изображений;
- размер входа и выхода;
- checksum manifest и PDF;
- класс ошибки без секретов и полного текста книги.

Полный текст книги, изображения, service token и PDF в логи не записываются.

Builder не отправляет отдельный error callback. При ошибке процесс в
`trans-api` остаётся незавершённым, а `trans-api` может повторить полную команду.

## 15. Временные файлы и безопасность

- каждая задача получает отдельный временный каталог;
- имя каталога генерируется сервисом, а не берётся из запроса;
- multipart filenames не используются как пути;
- сетевой доступ WeasyPrint к внешним URL запрещён;
- callback разрешён только на настроенный `TRANS_API_BASE_URL`;
- временные файлы удаляются после успеха и при штатной обработке ошибки;
- startup cleanup удаляет устаревшие каталоги старше настроенного TTL;
- входные лимиты применяются во время streaming upload, а не после загрузки
  всего файла в память;
- PDF и изображения не должны полностью удерживаться в RAM без необходимости.

```text
    unit/
    integration/
    fixtures/
```

Каждый модуль имеет одну ответственность. CLI-прототип пилота не переносится в
один production-файл.

## 17. Что использовать из существующего reference bundle

Reference находится в:

`docs/examples/translation-pipeline-pilot/`

### 17.1. `build_reflow_html.py`

Использовать как проверенный алгоритмический пример:

- структуру `Item` как основу `BuildElement`;
- сортировку и контроль порядка;
- классификацию headings/body/list/caption/note/code;
- объединение последовательных list items;
- неделимые figure blocks;
- HTML escaping;
- Jinja2/CSS-подобную потоковую вёрстку;
- правила `break-inside`, `break-after`, `orphans`, `widows`;
- сохранение моноширинного кода;
- вставку изображений по месту.

Не переносить:

- чтение локального Markdown;
- чтение исходного PDF;
- восстановление данных через PyMuPDF;
- абсолютные файловые пути;
- argparse CLI;
- специальные ключи конкретной пилотной книги;
- headless Chrome как production renderer.

В production все элементы уже приходят во входном API, а PDF создаёт
WeasyPrint.

### 17.2. `export_markdown_manuscript.py`

Не использовать в production pipeline. Он полезен только как пример состава
элемента: stable key, текст, bbox, style, figure reference. В сервисе основной
контракт — типизированный JSON `request`, а не Markdown.

### 17.3. `design/pdf-layout-requirements.md`

Перенести в acceptance tests:

- отсутствие висячих заголовков;
- совместный перенос рисунка и подписи;
- единые шрифты и поля;
- запрет индивидуального уменьшения абзацев;
- отсутствие неожиданных пустых страниц;
- проверку наличия всех изображений.

### 17.4. Принцип переноса

Reference-скрипты не запускаются из production-кода и не копируются целиком.
Из них извлекаются чистые алгоритмы, покрываются тестами и размещаются в
соответствующих модулях `ordering.py`, `layout.py`, `html_renderer.py` и
`pdf_validator.py`.

### 18.2. API tests

- корректный multipart получает `202`;
- повреждённый JSON получает `400`;
- пропуск sequence получает `422`;
- отсутствующее изображение получает `422`;
- слишком большой вход получает `413`;
- заполненная очередь получает `429`;
- повтор идентичной команды не создаёт второй job;
- конфликтующее содержимое того же `processId` получает `409`.

### 18.3. Integration tests WeasyPrint

Fixture 1:

## 20. Критерии готовности

- сервис не имеет зависимостей от SQL, БД и S3;
- весь вход приходит одним POST;
- вход содержит полный `elements[]` и все изображения;
- ZIP не используется;
- после `202` builder не запрашивает дополнительные данные;
- элементы вставлены строго по непрерывному `sequentialNumber`;
- builder не выбирает и не изменяет переданный текст;
- существует только один режим сборки и один renderer WeasyPrint;
- заголовок не остаётся без следующего блока;
- рисунок и подпись не разделяются;
- не помещающийся рисунок переносится или пропорционально уменьшается;
- итоговый PDF проходит независимую проверку;
- результат отправляется одним POST с raw `application/pdf` body;
- builder не создаёт бизнес-статусы и не хранит постоянные данные;
- reference-скрипты описаны и перенесены только как тестируемые алгоритмы;
- тесты подтверждают отсутствие перестановок, пропусков текста и изображений.
